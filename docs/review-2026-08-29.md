# Code review — 2026-08-29

**Status:** Historical snapshot, not current implementation guidance. Several
findings were addressed after the reviewed commit, and proposed mechanisms must
be reassessed against `docs/design.md` before implementation.

**Scope:** whole project at commit `318381f` — `extension.ts`, all six `src/` modules,
`test/`, `bin/`, container wiring, `README.md`, `docs/poc-design.md`.
**Test suite:** 62/62 passing.

**Questions asked:** Is the project simple and straightforward? How can it be made
more useful?

---

## 1. Verdict

The architecture is simple. The implementation has started to leak.

The core idea is disciplined, and the design rule ("Herdr owns runtime truth") is
respected in code, not only in prose. About 1,900 lines total, no database, no
queue, no parallel lifecycle.

`src/goal-store.js` is the strongest file in the project: atomic write plus
containing-directory fsync, field allowlists on every record type, per-key write
serialization, and journal tail repair. Careful, boring, correct.
`src/herdr-client.js` and `src/review-turn.js` are small and single-purpose.

Nearly all of the complexity is concentrated in `extension.ts`.

## 2. Where simplicity leaks

### 2.1 Three representations of one concept

`extension.ts:75-1116` holds the entire state machine in one closure with fourteen
mutable variables. Three of them track the same thing — which pane is currently
under review:

- `preparingReviewPane`
- `activeReviewPane`
- `reviewTurn.paneId` (inside `ReviewTurnFence`)

Each is mutated in roughly five places: `drainSignals`, `handleSignalOnce`,
`agent_settled`, every decision tool, and `session_shutdown`. Every future change
must reason about all three staying consistent.

This is the single biggest simplicity liability in the project.

### 2.2 Duplicated scheduling predicate

`extension.ts:227-232` and `extension.ts:244-249` contain the same filter verbatim.
It decides which workers are eligible for review. If one copy drifts from the
other, workers silently stop being reviewed — a failure with no error and no log.

### 2.3 Two live views of the same field

`activeBindings()` (`extension.ts:125`) spreads runtime state into binding copies,
while `runtimeFor(binding)` re-fetches the live object. `extension.ts:231` reads
`runtimeFor(worker).awaitingHuman` on a `worker` that already has `awaitingHuman`
spread into it. Both readings are available at every call site; only one is
current. Nothing marks which is which.

### 2.4 Five near-copies of the decision epilogue

`supervisor_leave`, `supervisor_steer`, `supervisor_ask_human`,
`supervisor_recover`, and `supervisor_finish` each repeat the same sequence:

guard fence → look up binding → mode check → `recordDecision` → `cacheCheckpoint`
→ clear `pendingCursor` → `scheduleReview` → `close` fence → `armReviewTimer` →
assemble warning string → format model-facing instruction text.

A single `applyDecision()` helper would remove roughly 150 lines and make the
actual differences between the five decisions visible instead of buried in
boilerplate.

### 2.5 Policy encoded as one unreviewable string

`extension.ts:1060` is a single-line string literal of about 3,000 characters
carrying the entire supervisor contract: when to clarify, when to steer, what
counts as evidence, how to speak to the human. It cannot be diffed line by line,
reviewed in isolation, or tested.

The same problem in miniature appears in the repeated model-facing epilogues
("End this supervisor turn now. Wait for Herdr's next worker event; do not poll.")
copied into roughly ten tool results that must stay in sync by hand.

### 2.6 The central domain object is untyped

`extension.ts` is a TypeScript file, but `binding` flows through about forty
functions as implicit `any` — e.g. `function runtimeFor(binding)` at
`extension.ts:95`. The `src/` modules are plain `.js` with no types at all. The
one object every part of the system depends on has no declared shape.

### 2.7 The README is a changelog

`README.md` is 240 lines of stage-by-stage narrative ("Stage 2a…", "Stage 5
removes the old shared binding file…"). A newcomer cannot distinguish what is true
now from what was true three stages ago. This costs more straightforwardness than
any individual code issue.

## 3. Claim that does not match the code

`README.md:79-80` states that "repeated ineffective steering causes the supervisor
to ask the human instead of looping forever."

No steer counter exists anywhere in the codebase. The only related mechanism is
`missingDecisionRetries` (`extension.ts:1085`), which counts reviews that ended
*without* a decision — not repeated ineffective decisions.

The property is currently prompt-dependent, not structural. See §4.4.

---

## 4. How to make it more useful

Ranked by leverage.

### 4.1 Stop discarding the audit trail

`journal.jsonl` is written on every decision, and `loadSupervisorGoals` returns a
`completed` set. Neither is read anywhere outside tests (verified by grep for
`readAudit` and `.completed`). The project pays the full write cost for zero read
value.

Add `herdr-supervisor journal <goalId>` and `herdr-supervisor completed`, plus a
"what happened while you were away" digest at session start. The data is already
on disk and already validated — this is the cheapest available win.

### 4.2 Do not let a review turn lock out the human

`activeReviewPane` hard-rejects `supervisor_start_goal` (`extension.ts:437`),
`supervisor_update_goal` (`extension.ts:647`), and even unscoped
`supervisor_status` (`extension.ts:711`).

At three workers this is invisible. At ten, the human is frequently told to
"finish the current review first" for an action unrelated to that review. Queue
these instead of rejecting them, and always permit read-only status.

### 4.3 Make the "any CLI" claim real

`README.md:24` promises Codex, Claude Code, Pi, or OpenCode workers. In practice:

- only Codex yields message-level evidence (`src/observation.js:117`);
- everything else degrades to terminal scraping;
- `recoveryRequest` refuses non-Codex sessions outright (`src/supervision.js:87`);
- `supervisor_start_goal` hardcodes `kind: "codex"` (`extension.ts:510`).

`observeWorker` is already shaped as an adapter switch, so adding a Claude Code
JSONL reader is a contained change that multiplies the usable worker pool. Until
that exists, correct the README.

### 4.4 Make the anti-loop guarantee structural

Persist a steer count per goal in `current.json` and force `ask_human` after N
ineffective steers. This converts the `README.md:79-80` claim from a hope into a
mechanism, and directly bounds model cost.

### 4.5 Notify out of band on `ask_human`

A sleeping supervisor is only valuable if the human does not have to watch the
pane. Today the question lands in the Pi session and waits indefinitely. A hook —
bell, webhook, or Herdr status badge — closes the unattended-operation loop that
is the entire premise of the project.

### 4.6 Produce a completion artifact

On `accept`, the binding simply vanishes from the active set. Write a short goal
report (objective, criteria, evidence, decision timeline) so completed work
outlives the session.

### 4.7 Explicitly not recommended

Goal dependencies, sub-goals, or a task graph. The design rule at `README.md:241`
is correct and the project should keep refusing these.

## 5. Suggested first move

The highest-value single refactor is collapsing `preparingReviewPane`,
`activeReviewPane`, and `ReviewTurnFence` into one review-turn object that owns
the pane, the phase, and the fence — then routing all five decision tools through
one `applyDecision()`.

That removes roughly 200 lines from `extension.ts` and makes §2.2 and §4.4
straightforward instead of risky.

The read-side surfaces in §4.1 are a safer starting point: purely additive, and
they cannot destabilize a live supervisor.

## 6. Later design decision

Do not implement this review as a backlog. Its lasting value is the method:
look for duplicated state, duplicated scheduling rules, misleading claims, and
features whose operational value is unclear. The current project rule is to
solidify common deterministic foundations and leave uncommon recovery or
workflow choices to model judgment. Revalidate every recommendation against
current code and repeated live evidence before turning it into a feature.
